# Releasing Markie

This is the authoritative desktop release runbook. A release is complete only when the new build
is pushed, locally verified, uploaded, publicly verified, and confirmed from the previous app
version through **Check for Updates**.

## Stable release contract

`server/download-manifest.json` is the one source of truth for the stable channel. It owns:

- the public Backblaze bucket and base URL;
- updater feed paths;
- which platforms are public;
- permanent website and email download routes;
- the permanent machine-readable release route.

`electron-builder.config.cjs` reads that manifest. The server reads the same file. Never duplicate
the bucket, feed path, or direct artifact URL in website code, email templates, docs, or release
scripts. Production also rejects `MARKIE_SITE_URL` or `MARKIE_DOWNLOAD_BASE` overrides that would
drift from this manifest. Those guards belong to the official deployment, which is what the server
is whenever `MARKIE_OFFICIAL` is unset or `1`. A self-hosted server (`MARKIE_OFFICIAL=0`,
docs/SELF-HOSTING.md) serves no download routes and redirects them to `https://markiedocs.com/download`.

Permanent links:

| Consumer | Stable URL | Purpose |
| --- | --- | --- |
| Websites, docs, campaigns, and generic email CTAs | `https://markiedocs.com/download` | Human-facing current download page |
| Apple Silicon direct CTA | `https://markiedocs.com/download/mac` | Redirects to the newest public Apple Silicon DMG (Markie RS from 0.10.0) |
| Intel Mac direct CTA | `https://markiedocs.com/download/mac-intel` | Redirects to the newest public x64 DMG, from `mac-intel/latest-mac.yml` since the Mac cutover |
| Windows direct CTA | `https://markiedocs.com/download/windows` | Redirects to the newest public signed installer |
| Linux direct CTA | `https://markiedocs.com/download/linux` | Redirects to the newest public AppImage, once Linux has a stable release |
| Debian and Ubuntu direct CTA | `https://markiedocs.com/download/linux-deb` | Redirects to the newest public `.deb` from the same `latest-linux.yml` |
| Versionless "get Markie" link | `https://markiedocs.com/download/latest` | The build for the visitor's OS when it is offered, Apple Silicon otherwise |
| Integrations and release checks | `https://markiedocs.com/download/latest.json` | Current version, routes, and resolved artifacts |

Versioned Backblaze artifact URLs are implementation details. Each platform has its own stable
updater feed, generated by Electron Builder: `mac/latest-mac.yml` for macOS (Apple Silicon, and
since the [Mac cutover](#mac-cutover-0100) `mac-intel/latest-mac.yml` for Intel), `windows/latest.yml`
for Windows, and `linux/latest-linux.yml` for Linux (both the AppImage and the `.deb`). The release runner publishes these mutable feeds only after all immutable artifacts are
uploaded and reachable, and a packaged install learns which one it follows from the `app-update.yml`
Electron Builder writes at pack time from this manifest.

## Human checkpoint

Preparing and verifying a release is safe to run autonomously. Publishing, rolling back, tagging,
creating a GitHub release, and deploying the production server are external-production actions.
An agent must get an explicit release instruction before running them. The publish command still
requires the exact version in `--confirm-public-release=<version>`.

Kirby saying "release X.Y.Z" is that instruction for the early-access publish of X.Y.Z **and** for
its timed promotion to stable after the soak, unless he holds it. The promotion itself runs
unattended through `release:promote-due`. This depends on the amendment recorded as pending in
`CONSTITUTION.md` ("Pending amendment: release approval scope"); until Kirby ratifies it, ask before
the promotion as well.

## Release stages

Every release moves through three stages:

| Stage | Who sees it | How it gets there |
| --- | --- | --- |
| 1. Super nightly | Kirby only, through the authenticated private gateway | `node scripts/private-release.mjs build`, `verify`, then `publish-private`, run by the authorized root agent. See `docs/PRIVATE_RELEASES.md`. Unchanged by this pipeline. |
| 2. Early access | Users who turned on **Get new versions early** | `release:publish:early:mac` / `:win` / `:linux` when Kirby says "release X.Y.Z" |
| 3. Stable | Everyone, the website, `latest.json` | `release:promote-due` after the soak, or `release:promote` by hand |

Stage 3 never builds anything. It points the stable feeds at the files stage 2 already uploaded.

On the Mac, stage 1 is no longer an Electron build. Since 2026-11-24 the super-nightly lane carries
the Rust app (`docs/PRIVATE_RELEASES.md`, "On the Mac, this lane now carries the Rust app"), and an
Electron super-nightly is published there only as its roll back. Stages 2 and 3, and everything
about Windows and Linux, are as before.

Stage 1 does not feed stage 2 that way. A super-nightly build has its own version
(`X.Y.Z-super-nightly.N`), its own builder config, a private marker, and a ZIP-only feed on the
private gateway. Its verification requires that marker and version, so a stable or beta artifact
cannot pass as a private build, and the reverse is never attempted. Stage 2 is a fresh
`release:prepare:mac` / `release:prepare:win` / `release:prepare:linux` build of the stable-numbered version. Private builds
also cannot join early access: `main.js` refuses the channel switch in a private build.

The private lane writes its output under `.release/private-artifacts/` by default. The early-access
commands only read `.release/<version>/early.json`, so they never touch it.

### How promotion ships the same bits

Early releases carry their final version, `0.9.0` and never `0.9.0-beta.1`. Electron Builder
writes `latest-mac.yml` (`latest.yml` on Windows, `latest-linux.yml` on Linux) for that build. The
early publish uploads the artifacts and then that exact feed text under the early name:
`mac/beta-mac.yml`, `windows/beta.yml` and `linux/beta-linux.yml`. Promotion later uploads the same
text under the stable name.

This works because of how electron-updater reads an S3 feed:

- The S3 provider is a `GenericProvider`. It fetches `<channel>-mac.yml` on macOS,
  `<channel>.yml` on Windows and `<channel>-linux.yml` on Linux x64, and offers the version inside when it is semver-greater than the
  running app. It does not care whether the version has a prerelease tag.
- `allowPrerelease` is only consulted by the GitHub providers, so it plays no part here.
- A feed file does not name itself, and its artifact URLs are relative. Both feeds live in the same
  directory, so they resolve to the same objects. `earlyTarget()` refuses a manifest where they do
  not.
- Setting `autoUpdater.channel` turns `allowDowngrade` on inside electron-updater. `main.js`
  assigns the value from `updaterSettingsFor()` after the channel, so stable installs never
  downgrade.

A stable install only ever reads `latest-mac.yml`, `latest.yml` or `latest-linux.yml`. Nothing in
stage 2 writes those.

### Early-access channel

The channel is still called `beta` on disk and in the feed names. Three properties keep it safe:

1. **Opt-in only.** The default is stable. The single way in is the **Get new versions early**
   toggle in Settings, Advanced. It writes `update-channel.json` in userData, with the original
   `beta` key, so a file written by an older build reads the same. `channelFor()` treats anything
   that is not literally `true` as stable.
2. **Unlisted.** The early feeds are recorded in `betaChannel` in `server/download-manifest.json`
   (`feed` for macOS, `windowsFeed` for Windows, `linuxFeed` for Linux) and are deliberately **not** `platforms` entries.
   The website and the share emails render from `platforms`, so nothing public can point at an
   early build. `release:preflight` fails if a beta platform entry ever appears, or if either early
   feed stops being a sibling of its stable feed.
3. **Reversible.** Turning the toggle off records the version the user was running as
   `leftEarlyFrom`. That exact build is allowed to downgrade to current stable, so a user who leaves
   on a build we later withdraw is not stranded above stable. A legacy `X.Y.Z-beta.N` build always
   qualifies. Once the install runs any other version, the marker is cleared.

Installed apps older than this change only allow that downgrade for prerelease versions. A user on
one of those who leaves early access while on a stable-numbered early build stays on it until
stable catches up.

### Stage 2: publish to early access

Prepare exactly as for a stable release (sections 1 to 3 of the macOS runbook, and steps 1 and 2 of
the Windows and Linux runbooks). Then:

```sh
npm run release:publish:early:mac -- --confirm-public-release="$MARKIE_RELEASE_VERSION"
npm run release:publish:early:win -- --confirm-public-release="$MARKIE_RELEASE_VERSION"
npm run release:publish:early:linux -- --confirm-public-release="$MARKIE_RELEASE_VERSION"
```

These are `release:publish:<platform> -- --early`. Use the named
scripts so a forgotten flag cannot publish straight to stable.

The guards are the same as a stable publish: the exact version, clean pushed `main`, credentials,
and exact-commit evidence matching the files on disk. The runner then:

1. checks the version is newer than the stable feed and not older than the early feed;
2. saves the early feed it is about to replace as `.release/<version>/previous-beta-mac.yml`,
   `previous-beta.yml` or `previous-beta-linux.yml`, once, so a re-run cannot overwrite it;
3. uploads the artifacts and blockmaps, then downloads each and verifies its full SHA-512;
4. uploads the early feed last and waits for it to propagate;
5. writes `.release/<version>/early.json`.

The stable feeds, the website, and `latest.json` are not touched.

`early.json` holds `publishedAt`, `soakUntil`, `soakDays`, `held`, the commit, and for each platform
the feed hash and every artifact's size and SHA-512. `.release/` is gitignored, so this state lives
on the release machine. Promotion has to run on the machine that published early.

### Soak

The soak is `betaChannel.defaultSoakDays` in the manifest, 3 days today. Override it per release
with `--soak-days=<n>` on the early publish. Fractions work: `0.5` is twelve hours.

The clock is per release. Publishing the second platform restarts it from that publish, and both
platforms promote together. A newer early release replaces the older one: the older one is never
promoted, and the newer one starts its own soak.

### Hold

```sh
npm run release:hold -- --version=0.9.0 --reason="crash on launch in 14.2"
npm run release:unhold -- --version=0.9.0
```

A hold stops promotion, including `release:promote --now`. Unholding does not restart the clock: if
the soak already ended, the next scheduler run promotes.

### Stage 3: promote

It is built to run every hour from a scheduler. Nothing in this repo schedules it, so run it by hand
or from a scheduler set up on the release machine:

```sh
npm run release:promote-due
```

It is idempotent. When nothing is due it reads only `.release/`, touches neither git nor the
network, and prints one line such as `0.9.0 soaking until 2026-10-23T12:00:00.000Z (31h left)`.
Every run appends its line to `.release/promote-due.log`. It exits non-zero only when a due
promotion fails.

By hand, before or after the soak:

```sh
npm run release:promote -- --confirm-promote=0.9.0          # refuses during the soak
npm run release:promote -- --confirm-promote=0.9.0 --now    # skips the soak only
```

Promotion refuses when the release is held, withdrawn, superseded, or a prerelease. It also refuses
when the early feed in the bucket names a different version, and records it as superseded so the
scheduler stops retrying. A missing or unreadable early feed is a plain failure that the next run
retries. Otherwise it:

1. checks `main`, a clean tracked tree, and that the release commit is on `origin/main`;
2. checks the saved early feed against `early.json` and the live early feed against both;
3. downloads every artifact and blockmap again and compares its SHA-512 with the evidence;
4. saves the current stable feed as `previous-latest-mac.yml`, `previous-latest.yml` or
   `previous-latest-linux.yml` (there is none before the first Linux release);
5. uploads the stable feeds last, after every platform has passed;
6. runs the same checks a stable publish runs: feed propagation, `/download`, every download route,
   `/download/latest.json`, the Windows public feed, and the Linux feed and routes;
7. writes `public.json`, `public-windows.json` and `public-linux.json`, and marks `early.json`
   promoted.

Before Linux goes stable for the first time, promotion also asks `/download/latest.json` whether the
deployed server knows Linux (it lists it under `awaitingFirstRelease`). An older server does not, and
promotion stops before writing any feed and says to deploy the server first.

A promotion that stopped halfway is finished by running it again. A platform whose stable feed
already holds the identical early feed is skipped.

After promotion, run the user-level checks in section 5 of the macOS runbook, step 5 of the
Windows runbook, and step 6 of the Linux runbook. They read the saved `previous-latest*.yml`, so they test the update from the
previous stable release.

### Rollback at each stage

| Stage | Command | Effect |
| --- | --- | --- |
| Early, before promotion | `npm run release:rollback:early -- --confirm-rollback=<version>` | Restores the saved previous early feed on each platform, or points the early feed at current stable when there was none. Marks the release withdrawn, so it never promotes. |
| Stable, after promotion, macOS | `npm run release:rollback:mac -- --confirm-rollback=<version>` | Restores `previous-latest-mac.yml`, then verifies the website routes. |
| Stable, after promotion, Windows | `npm run release:rollback:win -- --confirm-rollback=<version>` | Restores `previous-latest.yml`. |
| Stable, after promotion, Linux | `npm run release:rollback:linux -- --confirm-rollback=<version>` | Restores `previous-latest-linux.yml`. The first Linux release has none; withdrawing it means deleting `linux/latest-linux.yml` from the bucket by hand. |

Early users who already installed a withdrawn build keep it until the next release. The channel
deliberately does not downgrade users who are still opted in, because an old early feed could
otherwise pull them back by several versions.

A stable rollback leaves the early feed alone. Withdraw early as well, or ship a fix, so early users
do not stay on the build stable just left.

Versioned artifacts stay in storage at every stage. Removing them is a separate destructive storage
operation and is normally unnecessary.

### Direct stable publish

`release:publish:mac`, `release:publish:win` and `release:publish:linux` without `--early` still
publish straight to stable.
Use them only when Kirby asks for a release to skip early access. Afterwards the runner brings the
early feed up to the same version when it is missing or older, because early-channel installs read
only the early feed and would otherwise never see a stable hotfix.

### Legacy `X.Y.Z-beta.N` builds

The old prerelease path still works and never promotes:

```sh
npm run release:version -- 0.5.0-beta.1
npm run release:prepare:mac
npm run release:publish:mac -- --confirm-public-release=0.5.0-beta.1
```

`assertVersion` accepts `X.Y.Z-beta.N` and no other prerelease tag. Electron Builder derives the
channel from the tag and writes `beta-mac.yml`, which `macFeedFile()` selects. `0.5.0-beta.1` sorts
below `0.5.0`, so the stable release afterwards is not read as a downgrade. `--early` refuses a
prerelease version.

## Full macOS release

### 1. Re-ground and inspect status

```sh
git switch main
git pull --ff-only
npm ci
npm run release:status
```

Confirm the package version, current commit, public feed version, and website version. A missing or
stale website version means the server route must be deployed before publishing a new app feed.

**Deploy the server before shipping an app build whose sign-in changed.** The desktop Google flow is
split across both: the app mints a `state` nonce and refuses any `markie://auth` deep link that does
not carry it back, and only a deployed server echoes that nonce. Ship the app first and Google
sign-in fails for everyone who updates, with no way to recover from inside the app. `release:status`
does not catch this, so check it by hand whenever `server/src/desktop-auth.ts`,
`src/lib/auth-state.ts`, or the bridge routes in `server/src/index.ts` have changed since the last
deploy.

The hosted server's env, secrets, and deploys are managed in the private `ZVN-DEV/zvn-infra` repo
(Kamal app `markie-api`), not here. See `kamal/apps/markie-api/` and `docs/migrations/markie-api.md`
there. Compare what is deployed against `git log -- server/` and deploy anything behind before
publishing. Then check that `https://api.markiedocs.com/health` returns 200. The entrypoint migrates
the schema on every boot, so a bad migration takes the service down at start.

The server image also carries the web app at `/app` (`server/src/web-app.ts`). Before building the
image, run `npm ci && npm run build:web` at the repo root: it writes the build into `server/web-dist/`,
which `server/Dockerfile` copies in, and the image is still built with `server/` as its context.
Build from that working tree, not a clean `git archive` of `server/`, because the build output is
gitignored. Without the step the image still builds and `/app` answers 404.

For Markie Cloud, set `MARKIE_DOCS_ORIGIN=https://markiedocs.com`. The website proxies `/d`, `/s`
and `/app` to this server. The app calls `https://api.markiedocs.com` directly, and sign-in (Google
and the emailed code) stays there with its session cookie. Unset, everything stays on the server's
own origin, which is what a self-hosted server wants.

Order matters. Deploy the server first, then the website's `/app` rewrite, then set the variable.
After setting it, check that the proxy's requests are told apart from direct ones:
`curl -sI -H 'Sec-Fetch-Mode: navigate' https://markiedocs.com/app` must answer 200, not a 302 to
itself, and the same request to `https://api.markiedocs.com/app` must answer 302 to
`https://markiedocs.com/app`. If the first loops, unset the variable. After the deploy, check that `https://markiedocs.com/app`
signs in with a code and with Google, and opens a document.

### 2. Set the version once

```sh
export MARKIE_RELEASE_VERSION=0.2.10
npm run release:version -- "$MARKIE_RELEASE_VERSION"
```

This updates `package.json`, the root entries in `package-lock.json`, and `mcp/package.json`. Do not
edit those versions separately.

Write release notes from the actual diff since the previous `v<version>` tag. Commit with the Lore
protocol, push `main`, and wait for required CI. The release runner refuses a dirty tree or a commit
that is not exactly `origin/main`.

### 3. Prepare and verify without uploading

```sh
npm run release:prepare:mac
```

This command:

1. runs `npm run release:preflight` for renderer/Electron tests, MCP tests, server tests, lint, and
   the static build;
2. deletes only generated `dist/` output;
3. builds both macOS architectures, signs and notarizes the app bundles, then signs, notarizes, and
   staples the DMG containers, all with `--publish never`;
4. runs package and native launch smoke checks for Apple Silicon and Intel/Rosetta;
5. regenerates DMG blockmaps and updater hashes after stapling, then verifies `codesign`, Gatekeeper
   acceptance, DMG stapling, sizes, updater-feed contents, blockmaps, and SHA-512 hashes;
6. writes ignored evidence to `.release/<version>/local.json` for the exact commit.

The launch smoke fails on a main-process throw even when a window comes up. `main.js` logs
`uncaughtException` and `unhandledRejection` to `markie-crash.log` and keeps running, so every launch
gate reads that log from its throwaway profile and prints the error. The same launch runs on every
PR as the required `mac-launch-smoke` and `launch-smoke` (Windows) checks. A packaging bug therefore
fails the PR that causes it, not the release. 0.9.0 reached this gate with a module missing from the
public asar because nothing had launched the public Mac build before it.

Passing `release:preflight` alone does **not** mean an artifact is signed, notarized, published,
uploaded, deployed, or approved. `release:prepare:mac` is the complete local gate.

The verification-only command is:

```sh
npm run release:verify:mac
```

### 4. Production publish checkpoint

Only after explicit approval. A normal release goes to early access first; see
[Stage 2](#stage-2-publish-to-early-access) and [Stage 3](#stage-3-promote). The direct stable
publish below is for a release Kirby asked to skip early access:

```sh
npm run release:publish:mac -- --confirm-public-release="$MARKIE_RELEASE_VERSION"
```

The runner rechecks clean pushed `main`, credentials, exact-commit evidence, signatures,
notarization, hashes, and the live website contract. It then:

1. saves the previous public updater feed under `.release/<version>/`;
2. uploads versioned DMGs, ZIPs, and blockmaps;
3. downloads every artifact and blockmap and verifies its full SHA-512 against the smoke-tested
   evidence;
4. uploads `latest-mac.yml` last, making the release visible to installed apps;
5. waits for feed propagation;
6. confirms `/download`, `/download/mac`, and `/download/latest.json` resolve the new release;
7. writes `.release/<version>/public.json`;
8. brings the early feed up to the same version if it was missing or older.

The old `npm run electron:release` command is now only an alias to this guarded publisher; it cannot
build and upload in one unverified step. Never use `electron-builder publish` as a dry run: its
standalone publish command uploads the supplied files even when passed `--policy never`.

### 5. Verify the updater notice as a user

Most of this is now automated:

```sh
npm run update:check
```

It downloads the **previous** public release from the same URL a user would, checks it still
passes Gatekeeper, launches it with a throwaway profile against the **live** feed, and waits for
the app to find, download, and offer the update on its own — no prompting, no stubs. It asserts the
notice names the new version and that the install button is offered. The version to update from is
read from `.release/<version>/previous-latest-mac.yml`; override with `--from <version>`.

What it deliberately does not do is click **Restart & Update**: the staged update is discarded with
the temporary profile, so the swap-and-relaunch is still verified by hand. After publication, launch
the previous public Markie version with a clean profile, choose **Markie > Check for Updates**, and
confirm:

1. the new version is found;
2. download completes;
3. the update-ready notice appears;
4. **Restart & Update** installs and relaunches once;
5. **About Markie** reports the new version;
6. file creation, opening, panel navigation, menu dismissal, and window dragging still work.

This is the final user-facing release checkpoint. Keep the screenshot or screen recording with the
release evidence.

### 6. Finalize source control

After public and updater verification:

```sh
npm run release:verify:public -- --version="$MARKIE_RELEASE_VERSION" --deep
git tag -a "v$MARKIE_RELEASE_VERSION" -m "Markie $MARKIE_RELEASE_VERSION"
git push origin "v$MARKIE_RELEASE_VERSION"
```

Create the GitHub release from that tag and attach or link the release notes. Do not attach unsigned
Windows artifacts, or Linux packages that did not pass `release:prepare:linux`.

Then put Kirby's own Mac back on the public lane, so he runs what everyone else now has:

```sh
npm run markie:use -- public
```

## Rollback

If the newly published feed must be withdrawn, explicitly approve rollback and run:

```sh
npm run release:rollback:mac -- --confirm-rollback="$MARKIE_RELEASE_VERSION"
```

This restores the exact previous `latest-mac.yml` saved before publication or promotion and verifies
the previous version through the public feed and website routes. The version comes from the
confirmation flag, so it still works after `main` has moved to the next version. Versioned artifacts
remain in storage; removing them is a separate destructive storage operation and is normally
unnecessary. See [Rollback at each stage](#rollback-at-each-stage) for the early feed.

## Mac cutover (0.10.0)

At 0.10.0, Apple Silicon Macs switch from Electron Markie to Markie RS, the Rust app, through the
normal updater. Intel Macs stay on Electron, which becomes "Markie for Intel Macs". Windows and
Linux are unchanged. Every platform ships as 0.10.0 at the cutover. After it, Markie RS and the
Electron builds can carry different versions.

The manifest declares the cutover in `macCutover` (version, bundle id, team). Everything below
reads it: the release runner, `electron-builder.config.cjs`, the server and `release:preflight`.
Markie RS uses the same bundle id, `com.zvn.markie`, and the same team, `3VU8SG5TD9`, so Squirrel
accepts it as an in-place update of Electron Markie.

### The feeds

| Feed | Who reads it | What it lists |
| --- | --- | --- |
| `mac/latest-mac.yml`, `mac/beta-mac.yml` | Every Electron Mac build older than 0.10.0, both arches, and Markie RS | The Rust arm64 ZIP and DMG, and one Electron x64 ZIP: the Intel bridge. Its version is the Rust version |
| `mac-intel/latest-mac.yml`, `mac-intel/beta-mac.yml` | Electron x64 builds from 0.10.0 on | The Electron x64 ZIP and DMG only |

electron-updater picks the file per machine (`MacUpdater.filterFilesForArch` in electron-updater
6.8.11). An Apple Silicon Mac, Rosetta included, takes the file with `arm64` in its name. An Intel
Mac drops every arm64 file and takes the x64 ZIP. `electron/release-cutover.test.ts` runs that real
code over the feeds the runner writes, and `release:verify:public` runs it over the public ones.

Every Electron Mac build made under the cutover has `mac-intel` baked into its `app-update.yml`.
The release runner builds Electron for x64 only and checks that path in the packaged app.

### The Intel bridge

The `mac/` feed carries one version, the Rust one. An Intel install older than 0.10.0 is offered
that version, downloads the x64 ZIP, and becomes the Intel build inside it. That build reads
`mac-intel/` from then on. So the x64 entry in `mac/` must always be an Electron x64 build at or
above 0.10.0. The runner keeps it that way:

- A **joint** release (Rust and Intel under one version, as 0.10.0 is) makes its own x64 ZIP the
  bridge, uploaded to both `mac/` and `mac-intel/`.
- A **Rust-only** release carries the bridge forward byte for byte from the stable `mac/` feed. It
  is downloaded and checked by SHA-512, never uploaded again. When the Rust version moves past the
  last Intel version, the x64 entry stays, so no old Intel Mac is stranded.
- An **Intel-only** release writes `mac-intel/` only. Old Intel installs reach the bridge first,
  then the newest Intel build through `mac-intel/`.

An old Intel install's update notice names the Rust version, the feed's. After the update, About
shows the Intel version it actually installed. An Electron x64 build at or above 0.10.0 must never
read `mac/`: it would be offered the Rust version and reinstall the bridge on every check. That is
why the runner refuses an x64 app whose `app-update.yml` does not point at `mac-intel/`.

### Steps, in order

1. **Server first.** Deploy the server from the release commit before either cutover feed goes
   stable. The Intel route then reads `mac-intel/latest-mac.yml`, and falls back to `mac/` while
   that feed does not exist (a 404), so deploying early is safe. Promotion and a direct publish
   stop unless `/download/latest.json` reports `macCutover: "0.10.0"`. The early publish does not
   need it.
2. **The Rust build.** On the Rust branch, `rust/scripts/public-release.sh` writes
   `rust/target/public/<version>/`: `Markie-<version>-arm64.zip`, `Markie-<version>-arm64.dmg`
   and `release.json` (`version`, `gitCommit`, and each file's name, size and base64 SHA-512).
   Both files must already be signed, notarized and stapled.
3. **The handoff check** against the release candidate, before anything public. See
   [Handoff check](#handoff-check) below.
4. **Version and prepare.** On `main`, with the release commit pushed:

   ```sh
   npm run release:version -- 0.10.0
   npm run release:prepare:mac -- --rust-dir=../markie-rs/rust/target/public/0.10.0
   ```

   `MARKIE_RUST_RELEASE_DIR` works instead of `--rust-dir=`. Prepare checks every Rust file against
   `release.json`, builds and notarizes Electron for x64 only, stages `dist/cutover/mac/` and
   `dist/cutover/mac-intel/` exactly as they will be uploaded, and records the release in
   `dist/mac-release.json`. It then checks the Intel app's signature, notarization and
   `app-update.yml`, and unpacks the Rust ZIP to check it is not Electron, is `com.zvn.markie`
   signed by `3VU8SG5TD9`, reports the release's version, passes Gatekeeper and is stapled.
5. **Early access**, then **promote**, exactly as any release:

   ```sh
   npm run release:publish:early:mac -- --confirm-public-release=0.10.0
   npm run release:promote -- --confirm-promote=0.10.0     # or release:promote-due after the soak
   ```

   Both feeds are uploaded after every artifact is downloaded again and checked by SHA-512, and
   `mac-intel/` is written before `mac/`, so an Intel install that takes the bridge finds its own
   feed already there. The saved previous feeds are `previous-latest-mac.yml` and
   `previous-mac-intel-latest-mac.yml`. The first release has no Intel feed to save.
6. **Verify in public:**

   ```sh
   npm run release:verify:public -- --version=0.10.0 --deep
   ```

   It checks both feeds, every file's size and SHA-512, that the bridge is no newer than
   `mac-intel/` and is its exact bytes when they share a version, electron-updater's choice on both
   arches, and that `/download/mac` serves the Rust DMG and `/download/mac-intel` the Intel DMG.
7. **As a user.** `npm run update:check` from 0.9.7 on Apple Silicon, then by hand: an Intel Mac,
   or an Intel build under Rosetta, on 0.9.7 updates to the Intel 0.10.0 build, and a second check
   from there finds nothing newer.

Later releases pick a kind with a flag:

```sh
npm run release:prepare:mac -- --rust-dir=<folder> --rust-only   # Markie RS alone, keyed by the Rust version
npm run release:prepare:mac -- --intel-only                      # Electron x64 alone, keyed by package.json
npm run release:verify:public -- --version=<rust> --intel-version=<intel> --deep
```

A Rust-only version must not reuse a number an Electron release will take: evidence under
`.release/<version>/` is keyed by version. Every Electron arm64 Mac artifact is refused under the
cutover, at prepare, at verification and at the upload itself: the only arm64 bytes that may reach
the bucket are the ones `release.json` names.

### Rollback

| Stage | Command | Effect |
| --- | --- | --- |
| Early, before promotion | `npm run release:rollback:early -- --confirm-rollback=0.10.0` | `mac/beta-mac.yml` goes back to what it held, or to stable. `mac-intel/beta-mac.yml` has nothing earlier and keeps 0.10.0 for early users. The release never promotes. |
| Stable | `npm run release:rollback:mac -- --confirm-rollback=0.10.0` | Restores `mac/latest-mac.yml` to the saved 0.9.7 feed, then verifies it. `mac-intel/` is left as it is. |

Users who already took the update keep it. An Apple Silicon Mac already on Markie RS stays there
until a newer Rust release. An Intel Mac already on 0.10.0 stays on its own feed. Withdrawing
`mac-intel/latest-mac.yml` would mean deleting it from the bucket by hand, which needs its own
approval and is normally unnecessary. Moving Apple Silicon users who already run Markie RS back to
Electron would take a new, higher-numbered Electron arm64 release, which the cutover forbids. That
is a release decision, not a rollback; the usual answer is a newer Rust build.

### What Intel users see

- On 0.9.x: the usual update notice, naming the Rust version (for 0.10.0 itself the numbers
  match). Restart & Update installs Markie for Intel Macs 0.10.0, which looks and works as
  before.
- On 0.10.0 and later: updates come from `mac-intel/` only, Electron x64 builds only.
- `/download/mac-intel` and the Intel card on the download page serve the Intel DMG throughout.
  Before the cutover is promoted they resolve it from `mac/`, after it from `mac-intel/`.

### Handoff check

`npm run cutover:check` proves an installed Electron Markie on Apple Silicon becomes Markie RS
through Check for Updates, on this Mac, before anything is public. It serves a local copy of what
`mac/` will hold (the Rust release candidate plus an Electron x64 ZIP as the bridge, written by the
runner's own feed code) on `127.0.0.1`, runs an Electron 0.9.7 arm64 build against it, and checks:

1. the app finds the update itself, downloads the Rust ZIP and not the x64 one, and raises the
   update-ready notice naming the release candidate;
2. with `--install`, Squirrel swaps the bundle, and the result is not Electron, reports the
   release candidate's version, and is `com.zvn.markie` signed by `3VU8SG5TD9` with an intact
   signature;
3. Markie RS starts from the swapped bundle and stays up.

```sh
npm run electron:build:mac -- --x64      # or any folder holding an Electron Markie-0.10.0-x64.zip
MARKIE_ALLOW_E2E=1 npm run cutover:check -- \
  --rust-dir ../markie-rs/rust/target/public/0.10.0-rc.1 \
  --intel-dir dist --build --install
```

A shipped 0.9.7 reads its feed from inside its signed bundle and cannot be pointed at a local one,
so `--build` builds 0.9.7 from this checkout with `electron-builder.update-harness.cjs`. That
build differs in one way: it carries the `markieUpdateHarness` marker, which lets
`electron/update-harness.js` take `MARKIE_UPDATE_HARNESS_FEED_URL`, and only a loopback `http` URL.
No release build carries the marker: `release:preflight` fails if the public config sets it, and
the runner refuses a packaged app that has it. The harness build is signed with the Developer ID in
the keychain and not notarized; set `CSC_NAME` if the keychain holds more than one. The check
refuses to start unless it is signed by `3VU8SG5TD9`, because Squirrel only accepts an update
signed like the running app.

It never touches an installed Markie. It refuses `/Applications` and `~/Applications` as the source
and as the app under test, runs a copy in a temporary folder with a throwaway profile, and saves and
restores Squirrel's install state, which the real Markie shares. With `--install`, Squirrel
installs when the old app quits, and the check starts Markie RS itself with `HOME` set to a
throwaway folder, so it cannot import the real profile. `--install=restart` clicks Restart & Update
instead and lets Squirrel relaunch Markie RS through LaunchServices, with the real `HOME`. That
needs `--allow-real-profile`.

## Windows release runbook

Windows is a public signed platform: `windows-x64` is `public` in the manifest, the installer is
signed through Azure Trusted Signing, and as of 0.5.0 a packaged Windows install updates itself from
`windows/latest.yml`. Linux has its own runbook below.

The list below is the checklist for **every** Windows release, not a one-time switch. All of it has
to hold on the exact release commit:

- a successful native launch smoke on Windows;
- a production Authenticode signature, verified against the signer subject recorded in the manifest;
- installer and update testing from the previous public Windows version;
- public artifact and feed verification equivalent to the macOS runner;
- an explicit production release decision.

The Windows build cannot be produced on the release machine. It is signed by Azure from CI, because
no certificate exists locally and putting one there is not the goal, so the local half of a Windows
release is not "build and upload" but "fetch what CI signed, prove it is what it claims to be, and
publish that".

### 1. Build and sign in CI

Dispatch `.github/workflows/windows-release.yml` on the release commit with `signing: azure` and
`publish_release: true`. It builds the installer, signs it with a short-lived GitHub OIDC credential
(no long-lived secret in the repo), verifies the signature, then installs, launches, and uninstalls
on a Windows runner before publishing the installer to the rolling `windows-signed` prerelease tag.
A run with `signing: none` produces an unsigned installer for testing and must never be published.

### 2. Fetch and verify locally, uploading nothing

```sh
npm run release:prepare:win
```

This downloads only the artifacts named for this exact version from the `windows-signed` tag
(installer, blockmap, feed) into `dist-windows/`, deliberately not `dist/`, which the macOS prepare
deletes wholesale. It then checks the feed version, every SHA-512, and the Authenticode subject
against `codeSigning.subject` in the manifest, and writes `.release/<version>/local-windows.json` for
the exact commit. `npm run release:verify:win` re-runs that verification on its own.

### 3. Production publish checkpoint

Publishing is an external-production action. It needs an explicit release instruction, and the
command needs the exact version. A normal release uses `release:publish:early:win` here and is
promoted later; see [Release stages](#release-stages). The direct stable publish is:

```sh
npm run release:publish:win -- --confirm-public-release="$MARKIE_RELEASE_VERSION"
```

The runner rechecks clean pushed `main`, credentials, and exact-commit evidence. It uploads the
installer and its blockmap, re-downloads each and verifies the full SHA-512 against the local
evidence, and only then uploads `windows/latest.yml`. The feed goes last for the same reason it does
on macOS: it is the pointer, and a pointer published before what it points at is a broken update for
everyone who checks in between. The upload uses a generated `publish-windows.json` config rather
than a command-line override, so a typo cannot write Windows artifacts over the macOS feed.

### 4. Verify in public

```sh
npm run release:verify:public:win -- --version="$MARKIE_RELEASE_VERSION" --deep
```

### 5. Verify the update as a user

Dispatch `.github/workflows/windows-update-check.yml`. It runs the same
`scripts/update-flow-check.mjs` macOS uses, on a Windows runner, which is real Windows: it downloads
the **previous** public installer from the same URL a user would, installs it, launches it against
the **live** feed with a clean profile, waits for the app to find and download the update on its
own, clicks **Restart & update**, and confirms the executable on disk reports the new version and
the app came back.

The assertions are shared with macOS on purpose (`scripts/lib/update-targets.mjs` holds the four
things that genuinely differ: obtaining the previous release, judging its signature, reading the
version off disk, and finding the relaunched process). A claim that holds on one platform and not
the other is then a real difference rather than a difference in what was checked.

Pass the previous public version as the workflow's `from` input:

```sh
gh workflow run windows-update-check.yml --ref main -f from=<previous version>
```

The runner has no `.release/` directory, so without `from` the check stops at "cannot tell which
version to update from" (the 0.5.4 release lost one run to this). Locally the version would be
read from `.release/<version>/previous-latest.yml`, saved by `release:publish:win`. A Windows
release is not complete until this passes.

### Withdrawing a Windows release

```sh
npm run release:rollback:win -- --confirm-rollback="$MARKIE_RELEASE_VERSION"
```

`release:publish:win` and `release:promote` both save the previous `windows/latest.yml` as
`.release/<version>/previous-latest.yml` before replacing it. The rollback republishes that exact
file and verifies the public Windows feed. Versioned artifacts stay in storage either way.

## Linux release runbook

Linux ships as an AppImage (the main download, and the package that updates itself in place) and a
`.deb` for Debian, Ubuntu and their derivatives, both x64 only. A deb install updates through
electron-updater too: it downloads the new `.deb` and installs it with `pkexec`, which asks for the
admin password, so it installs on **Restart & Update** and never silently on quit.

Linux packages are unsigned by design. There is no Gatekeeper or SmartScreen on Linux for a signature
to satisfy, and electron-updater checks the SHA-512 in `latest-linux.yml` before it installs
anything. What proves a Linux build is ours is the CI build evidence: the exact commit, the run, the
checks it passed, and the SHA-512 of each package, written beside a `SHA512SUMS` file. Every check
below runs against the downloaded bytes, not against what CI reported.

The Linux build cannot be produced on the release machine, which is a Mac, so it follows the Windows
shape: CI builds, the release machine fetches and verifies, then publishes.

### Going live for the first time

Linux first went stable in 0.9.2 (2026-10-27). `linux-x64` and `linux-x64-deb` are still `ready` in
the manifest, so condition 2 below is still open. The server offers a ready platform the moment its
stable feed exists, so the first stable promotion of Linux is what put it on the download page. No
manifest edit has to be timed against the upload. Two conditions:

1. Deploy the server from a commit that has this manifest before Linux is promoted to stable. The
   promotion checks this and refuses otherwise. The early publish does not need it.
2. After the first stable Linux release, flip both entries to `public` in a normal commit. From then
   on a missing Linux feed fails the release gates instead of quietly hiding Linux, exactly as it
   does for macOS and Windows.

### 1. Build in CI

On the release commit, already pushed to `main`:

```sh
gh workflow run linux-release.yml --ref main -f publish_release=true
gh run watch "$(gh run list --workflow linux-release.yml --limit 1 --json databaseId --jq '.[0].databaseId')"
```

`.github/workflows/linux-release.yml` builds both packages with `--publish never`, then:

- checks the unpacked package structure and launches it under xvfb;
- checks the AppImage's desktop entry (`text/markdown`, `x-scheme-handler/markie`,
  `StartupWMClass=markie`) and that its `app-update.yml` points at `linux/`;
- launches the AppImage itself, through the AppImage runtime, with Ubuntu's user-namespace
  restriction on;
- installs the deb with `apt-get install`, validates its desktop entry, launches `/opt/Markie/markie`,
  and removes it;
- writes `Markie-<version>-linux-build.json` and `Markie-<version>-linux-SHA512SUMS.txt`;
- uploads the packages, `latest-linux.yml`, the evidence and the checksums to the rolling
  `linux-built` prerelease tag.

`publish_release` defaults to false, and the upload only runs from `main`. A dispatch without it is a
test build. Pull requests that touch Linux packaging run the same build without uploading.

### 2. Fetch and verify locally, uploading nothing

```sh
npm run release:prepare:linux
```

This downloads only the files named for this exact version from `linux-built` into `dist-linux/`,
then requires the feed, the build evidence and the checksum file to agree with each other and with
the bytes on disk, requires every check in the evidence, and requires the build's commit to be the
release commit. It writes `.release/<version>/local-linux.json`. `npm run release:verify:linux`
re-runs the verification on its own.

### 3. Publish to early access

```sh
npm run release:publish:early:linux -- --confirm-public-release="$MARKIE_RELEASE_VERSION"
```

Same guards and order as the other platforms: the AppImage and the deb first, each downloaded again
and checked by SHA-512, then `linux/beta-linux.yml` last. The first Linux release has no stable feed
to compare against, which the runner allows only while Linux is `ready`.

### 4. Promote

`release:promote-due` promotes Linux with the other platforms when the soak ends, or by hand with
`release:promote`. Promotion writes `linux/latest-linux.yml` last and then waits until
`/download/linux` and `/download/linux-deb` redirect to the new packages. The server caches a resolved
release for five minutes and a missing feed for one, so that wait can take a few minutes.

### 5. Verify in public

```sh
npm run release:verify:public:linux -- --version="$MARKIE_RELEASE_VERSION" --deep
```

### 6. Verify the update as a user

From the second Linux release on, dispatch the Linux update check with the previous Linux version:

```sh
gh workflow run linux-update-check.yml --ref main -f from=<previous Linux version>
```

It downloads the previous public AppImage, runs it under xvfb against the live feed with a clean
profile, waits for the update on its own, clicks **Restart & update**, and confirms the AppImage on
disk reports the new version. The first Linux release has nothing to update from, so for it this step
is a manual install of the AppImage and the deb on a Linux desktop.

### Withdrawing a Linux release

```sh
npm run release:rollback:early -- --confirm-rollback="$MARKIE_RELEASE_VERSION"   # before promotion
npm run release:rollback:linux -- --confirm-rollback="$MARKIE_RELEASE_VERSION"   # after promotion
```

The first Linux release replaced nothing. Withdrawing it before promotion leaves it on the early feed
and marks it withdrawn so it never promotes. Withdrawing it after promotion means deleting
`linux/latest-linux.yml` from the bucket by hand, which is a destructive storage operation and needs
its own approval.

## API server deploy and rollback

> **2026-10-27: Markie Cloud runs on ZVN's own boxes, not Fly.** `markie-api` is a Kamal app on
> `zvn-apps-a`, with `zvn-apps-b` as standby, behind Cloudflare for SaaS. Its config, deploy, failover
> and rollback live in the private `ZVN-DEV/zvn-infra` repo: `kamal/apps/markie-api/` and
> `docs/migrations/markie-api.md`. The old Fly app has since been deleted. Check
> `https://api.markiedocs.com/health` for the service's health.
>
> The zvndev.com zone's WAF rules apply to `api.markiedocs.com`. A client blocked there gets
> Cloudflare's 403 and the box never sees the request.

The database is SQLite at `DB_PATH`, replicated by Litestream. Backups, restores, and data rollback
are in zvn-infra. Deploy the server before any client release that depends on it. Released apps
going back to v0.8.0 call this API, so treat any change that breaks the v0.8.0-era server tests as
a client-breaking change.

## Cloud hostname

`https://api.markiedocs.com` is the canonical Markie Cloud origin. The old Railway hostname
`https://api-production-602f.up.railway.app` survives only as a legacy alias in client code
(`electron/cloud-origin.json`), so sessions, documents and links recorded under it keep resolving.
markiedocs.com proxies `/download`, `/d`, `/s` and the `.well-known` files to `api.markiedocs.com`
through `vercel.json` in the markie-site repo.
