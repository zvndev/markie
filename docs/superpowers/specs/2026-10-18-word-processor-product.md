# Markie everyday word processor

Product and implementation contract requested by Kirby on October 18, 2026. This supersedes treating isolated codec milestones as completion of the product described in [the document-platform direction](../plans/2026-10-14-document-platform.md). Circular owns task status, dependencies, owners and execution evidence; this document defines product behavior and architectural boundaries, not a second backlog.

## Outcome and completion boundary

Build a slightly simplified Word-like document editor inside the existing Markie application, alongside its existing Markdown editor. Simplification applies to interface complexity, not ordinary writing capabilities. macOS and Windows desktop lead; shared core features also work on web. A successful test count, page-shaped canvas, text extractor or safe parser is not this product's definition of done.

Preserve the existing shell, activity rail, Library/Projects, Cloud, settings, themes, file ownership and optional accounts. Keep one shared compact formatting toolbar and native File/Edit/Format/Insert/Layout/Review/View menus. Browser uses the existing command palette. No Word ribbon/tab strip, replacement application, switch-back destination, or Markdown serializer for Office files.

The completed everyday product covers authoring, formatting, structuring, review, original-format saving, printing, discovery, connected documents, sharing and collaboration, protected storage and trusted interactive Darkmown. VBA/macros, embedded OLE applications, every historical Office field/control, arbitrary legacy layouts and font-independent pixel-identical Word pagination are not implied. Security/protection warnings remain legitimate; routine blank documents must not carry permanent generic compatibility banners.

## Acceptance journeys

1. **Write naturally.** Create a DOCX from New, type a ten-paragraph draft, split/join paragraphs, use Shift+Enter, select forwards/backwards across paragraphs, replace/delete/cut/paste, continue a list, exit it, undo/redo and keep the expected caret and formatting. Repeat relevant flows for RTF/ODT. Emoji, combining sequences and IME candidate confirmation must not corrupt text or create accidental paragraphs.
2. **Produce a professional document.** Create a proposal with title/headings, mixed formatting, highlights, nested numbered/bullet lists, indents/tabs, a link, a resized inline image and a formatted table. Set paper/margins/orientation; add sections, headers/footers/page numbers. Navigate outline and page/continuous views. Print/PDF contains the same supported content, including boundary-crossing tables/media, without app chrome.
3. **Edit received files.** Open provenance-recorded Word/LibreOffice-produced DOCX/RTF/ODT fixtures, edit supported features and reopen exported files in their producer. Untouched files remain byte-identical; unrelated package parts/metadata remain intact. Unsupported structures are preserved and constrained only when dependency analysis proves safety; otherwise protection is specific, actionable and non-destructive. Native DOC and rich HTML are dedicated codec deliverables, not extension relabeling.
4. **Review.** Add range-anchored comments, replies and resolution; track supported text/format edits; inspect original/final/markup and accept/reject one/all changes. Anchors map through edits, undo, save/reopen and collaboration. Review, local undo and durable history remain distinct.
5. **Keep work connected.** Retain an unsaved Markdown draft while opening DOCX/TXT/RTF/ODT/Darkmown. Switch through the existing Library and authorized in-app links without reload/lost buffers. Find by title/body/person/type and distinguish native files, recovery, owned cloud and shared sources. External web links still use the device browser.
6. **Share and coauthor.** Previous-collaborator autocomplete is account/server scoped and keyboard accessible; selecting a suggestion sends no invitation. Two authorized rich-document clients converge through edits, offline reconnect and server restart. Viewer/commenter permissions and revocation are enforced on the server, not merely hidden in UI. Snapshot copies and live collaboration remain visibly different.
7. **Use private and interactive documents.** Lock hides names/content/search/undo/media/runtime state; actual native protected-key release enables biometric convenience unlock. Darkmown media, local/shared state and API actions use explicit source/dependency-scoped trust and reviewed capabilities; secrets are never embedded into portable source.

## Architecture decision

**Decision:** evolve existing format-owned source engines behind a shared semantic editing/transaction layer. Reuse installed generic editing/selection/CRDT primitives where they fit; do not reuse another Office engine or convert every format through DOCX, HTML or Markdown. The source package and codec-owned preservation state stay authoritative.

**Drivers:** everyday writing correctness; lossless original-format handling; continuity with Markie and desktop/web sharing.

**Alternatives:** indefinitely extend paragraph DOM heuristics (cheap initially, brittle for cross-block history/review/layout); replace the application/editor stack (unnecessary regression and violates continuity); adapt the current shell/codecs with explicit source-mapped semantic transactions (chosen, more contract work but preserves proven components). A third-party Office engine conflicts with the explicit clean-room requirement. Existing TipTap/ProseMirror may supply generic input behavior, not Office parsing/writing authority.

**Consequences:** transactions and source mapping precede rich UI expansion; codec-specific source operations may be needed for structural split/join; imported unknown data is not automatically safe to edit around. Do not implement rich split/join by flattening text and repainting a lossy style projection. Native DOC writing and true page layout are substantial independent deliverables.

### Contract boundaries and checkpoints

- Keep Markdown source authoritative for Markdown; preserve TXT encoding/BOM/newlines and literal semantics. CSV/JSON/YAML/XML remain honest text/table-preview workflows, not spreadsheet/schema engines.
- Define an internal codec facade for inspect/open, precise document capabilities, source-mapped projection, transactions, text extraction, export preflight, candidate validation and save. Evolve `rich-document.ts` rather than introduce a second application session store.
- Logical selection contains block/inline position, anchor/focus direction and affinity. Ephemeral selection/transaction/history state is not written into file content or library records by default.
- Transactions return mapped selection, affected ranges, inverse/history grouping and capability consequences. Preserve direct formatting, inheritance/theme and viewing preferences separately. Composition is one transaction; a no-op creates no dirty generation/history item.
- Capabilities combine format, actual document content, selection, permissions and host state; distinguish editable, preservable-only, view-only, explicit-conversion and unsupported with reason codes. Recheck at execution/export, including private/inactive/modal/composing state.
- Semantic identities used by durable comments/collaboration need a reviewed persistence/migration strategy. Existing opaque session run IDs are not promoted silently.
- **Human checkpoints:** internal rich model extensions are presented separately for approval; database/recovery schema changes, server/MCP/deep-link/public commands, collaboration wire versions, vault key migration and external-effect permissions each require explicit shape review before implementation. Approval for an internal rich model does not approve cloud schema/protocol changes or public releases.
- First executable batch below uses existing document/file model and codec operations; no persisted schema, public API, dependency or stack change is required. A checkpoint blocks only its dependent lane, not safe unrelated local work.

## First implementation batch and ownership

This is the first **entry** into phase 2, not a claim that the whole continuous editor is finished:

- Input lane: a private normalized same-paragraph range-to-run edit helper; deterministic typed replacement/deletion/cut/paste through existing `replaceRichText`; Unicode-safe deletion, exact caret recovery, HTML-only clipboard non-destruction, composing Enter safety. Tests cover bold-to-italic selections and complete-run deletion without flattening. Cross-block edits/structural owners remain protected until their transaction contract is implemented.
- Controls lane: expose existing daily formatting actions at normal editor widths; move less common controls to real overflow only when needed. Preserve the same control instances, selection, keyboard/focus, themes and narrow layout. No extra toolbar or ribbon.
- Output/status lane: remove the unconditional output disclaimer from ordinary document editing. Show relevant output information at Print/Export, and specific document restrictions in accessible context. Do not remove genuine unsupported/protected-content diagnostics or silently enable unsafe output.
- Verification lane: actual real-input browser and packaged desktop scenarios for these changes, protected fixtures, retained Markdown, light/dark and 390px. Record missing native Windows/physical IME evidence rather than convert structural checks into a pass.

Leader owns integration, specification/tracker, shared-file conflict resolution, review, final verification and preview selection. Input owns only its private module/paragraph integration/tests; controls owns only shared toolbar/tests; leader owns workspace/output/Export glue. Reviewers do not edit the code they review. Later structural editing must not be approximated through current lossy replace-paragraph operations.

Executable first-batch guard: unknown/noncancelable input, composition reconciliation and browser span merging may not fall back to whole-paragraph reconstruction. Reconcile/reject if a source-preserving run edit cannot be proven. Mixed-run or inline-owner Enter/multiline operations must remain byte/history/selection neutral until codec-safe structural transactions exist; plain represented cases may stay enabled only with preservation tests. Tracking routes through a different paragraph-wide operation and needs its own preservation proof or a specific guard. Include no-op snapshot identity, generation and history assertions, not just equivalent visible text. These temporary structural limits keep the entry batch safe; they do not satisfy or replace phase 2's cross-block acceptance.

## Risks and verification

1. **Loss hidden behind successful reopen.** Own parser/writer can agree on the same omission. Mitigate with producer-generated fixtures, producer-side reopen/black-box rendered comparisons, explicit semantic assertions and unrelated-part byte checks; never inspect another Office engine's source/artifacts.
2. **Editor forks or loses formatting.** Unmapped DOM changes, composition, split/join or caret/history races can corrupt edits. Mitigate with normalized transactions, Unicode and IME sequences, forward/backward selections, grouped history, rich inline-owner fixtures, save/undo/reopen and source-lineage/no-op tests. Do not widen a document's editing safety gate to satisfy a toolbar test.
3. **Capability/security claim outruns implementation.** Partial pagination, binary snapshots, passphrase-only vaults and offline Darkmown can be mislabeled complete. Mitigate with per-journey exact-commit evidence, server authorization, scoped trust/key release and feature-specific completion gates. Missing Windows/browser/hardware evidence stays missing.

Run red-to-green targeted tests, `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, affected Electron/server/MCP suites and packaged workflows. Validate App menu/toolbar/palette equivalence, original-format export and reopened source semantics, storage/permission/save conflicts, unsaved buffer continuity, stale async results, keyboard/focus/accessibility, offline/cold startup and private revocation. Screenshots corroborate layout, not data integrity.

Performance measurement precedes optimization: record reference hardware and p50/p95 typing, open, reflow, search and recovery costs on short, 20-page and 100-page corpora, including CJK/RTL/emoji and tables/media. Initial product targets on the recorded reference desktop are p95 ordinary typing under 50ms, a supported 10MB/100-page open under 5 seconds and cancellable background extraction; adjust only by an explicit measured product decision. Budgets never justify data truncation or skipping safety validation.

## Definition of done

The full program is complete only when all seven acceptance journeys and the declared everyday-format matrix have exact-commit evidence on the required desktop surfaces, shared web behavior has its own evidence, and known ordinary-writing gaps no longer prevent those journeys. Partial batches remain partial. A quiet editor is a UI property; a safe document is a codec/security property; Word-like daily functionality is a product property. None substitutes for the others.
