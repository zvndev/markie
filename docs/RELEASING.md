# Releasing Markie

This is the authoritative desktop release runbook. A release is complete only when the new build
is pushed, locally verified, uploaded, publicly verified, and confirmed from the previous app
version through **Check for Updates**.

## Stable release contract

`server/download-manifest.json` is the one source of truth for the stable channel. It owns:

- the public Backblaze bucket and base URL;
- updater feed paths;
- which platforms are public;
- permanent website and email download routes;
- the permanent machine-readable release route.

`electron-builder.config.cjs` reads that manifest. The server reads the same file. Never duplicate
the bucket, feed path, or direct artifact URL in website code, email templates, docs, or release
scripts. Production also rejects `MARKIE_SITE_URL` or `MARKIE_DOWNLOAD_BASE` overrides that would
drift from this manifest. Those guards belong to the official deployment, which is what the server
is whenever `MARKIE_OFFICIAL` is unset or `1`. A self-hosted server (`MARKIE_OFFICIAL=0`,
docs/SELF-HOSTING.md) serves no download routes and redirects them to `https://markiedocs.com/download`.

Permanent links:

| Consumer | Stable URL | Purpose |
| --- | --- | --- |
| Websites, docs, campaigns, and generic email CTAs | `https://markiedocs.com/download` | Human-facing current download page |
| Apple Silicon direct CTA | `https://markiedocs.com/download/mac` | Redirects to the newest public DMG |
| Intel Mac direct CTA | `https://markiedocs.com/download/mac-intel` | Redirects to the newest public x64 DMG from the same `latest-mac.yml` |
| Windows direct CTA | `https://markiedocs.com/download/windows` | Redirects to the newest public signed installer |
| Integrations and release checks | `https://markiedocs.com/download/latest.json` | Current version, routes, and resolved artifacts |

Versioned Backblaze artifact URLs are implementation details. Each platform has its own stable
updater feed, generated by Electron Builder: `mac/latest-mac.yml` for macOS and `windows/latest.yml`
for Windows. The release runner publishes these mutable feeds only after all immutable artifacts are
uploaded and reachable, and a packaged install learns which one it follows from the `app-update.yml`
Electron Builder writes at pack time from this manifest.

## Human checkpoint

Preparing and verifying a release is safe to run autonomously. Publishing, rolling back, tagging,
creating a GitHub release, and deploying the production server are external-production actions.
An agent must get an explicit release instruction before running them. The publish command still
requires the exact version in `--confirm-public-release=<version>`.

Kirby saying "release X.Y.Z" is that instruction for the early-access publish of X.Y.Z **and** for
its timed promotion to stable after the soak, unless he holds it. The promotion itself runs
unattended through `release:promote-due`. This depends on the CONSTITUTION amendment proposed with
this pipeline; until Kirby ratifies it, ask before the promotion as well.

## Release stages

Every release moves through three stages:

| Stage | Who sees it | How it gets there |
| --- | --- | --- |
| 1. Super nightly | Kirby only, through the authenticated private gateway | `node scripts/private-release.mjs build`, `verify`, then `publish-private`, run by the authorized root agent. See `docs/PRIVATE_RELEASES.md`. Unchanged by this pipeline. |
| 2. Early access | Users who turned on **Get new versions early** | `release:publish:early:mac` / `release:publish:early:win` when Kirby says "release X.Y.Z" |
| 3. Stable | Everyone, the website, `latest.json` | `release:promote-due` after the soak, or `release:promote` by hand |

Stage 3 never builds anything. It points the stable feeds at the files stage 2 already uploaded.

Stage 1 does not feed stage 2 that way. A super-nightly build has its own version
(`X.Y.Z-super-nightly.N`), its own builder config, a private marker, and a ZIP-only feed on the
private gateway. Its verification requires that marker and version, so a stable or beta artifact
cannot pass as a private build, and the reverse is never attempted. Stage 2 is a fresh
`release:prepare:mac` / `release:prepare:win` build of the stable-numbered version. Private builds
also cannot join early access: `main.js` refuses the channel switch in a private build.

The private lane writes its output under `.release/private-artifacts/` by default. The early-access
commands only read `.release/<version>/early.json`, so they never touch it.

### How promotion ships the same bits

Early releases carry their final version, `0.9.0` and never `0.9.0-beta.1`. Electron Builder
writes `latest-mac.yml` (and `latest.yml` on Windows) for that build. The early publish uploads the
artifacts and then that exact feed text under the early name: `mac/beta-mac.yml` and
`windows/beta.yml`. Promotion later uploads the same text under the stable name.

This works because of how electron-updater reads an S3 feed:

- The S3 provider is a `GenericProvider`. It fetches `<channel>-mac.yml` on macOS and
  `<channel>.yml` on Windows, and offers the version inside when it is semver-greater than the
  running app. It does not care whether the version has a prerelease tag.
- `allowPrerelease` is only consulted by the GitHub providers, so it plays no part here.
- A feed file does not name itself, and its artifact URLs are relative. Both feeds live in the same
  directory, so they resolve to the same objects. `earlyTarget()` refuses a manifest where they do
  not.
- Setting `autoUpdater.channel` turns `allowDowngrade` on inside electron-updater. `main.js`
  assigns the value from `updaterSettingsFor()` after the channel, so stable installs never
  downgrade.

A stable install only ever reads `latest-mac.yml` or `latest.yml`. Nothing in stage 2 writes those.

### Early-access channel

The channel is still called `beta` on disk and in the feed names. Three properties keep it safe:

1. **Opt-in only.** The default is stable. The single way in is the **Get new versions early**
   toggle in Settings, Advanced. It writes `update-channel.json` in userData, with the original
   `beta` key, so a file written by an older build reads the same. `channelFor()` treats anything
   that is not literally `true` as stable.
2. **Unlisted.** The early feeds are recorded in `betaChannel` in `server/download-manifest.json`
   (`feed` for macOS, `windowsFeed` for Windows) and are deliberately **not** `platforms` entries.
   The website and the share emails render from `platforms`, so nothing public can point at an
   early build. `release:preflight` fails if a beta platform entry ever appears, or if either early
   feed stops being a sibling of its stable feed.
3. **Reversible.** Turning the toggle off records the version the user was running as
   `leftEarlyFrom`. That exact build is allowed to downgrade to current stable, so a user who leaves
   on a build we later withdraw is not stranded above stable. A legacy `X.Y.Z-beta.N` build always
   qualifies. Once the install runs any other version, the marker is cleared.

Installed apps older than this change only allow that downgrade for prerelease versions. A user on
one of those who leaves early access while on a stable-numbered early build stays on it until
stable catches up.

### Stage 2: publish to early access

Prepare exactly as for a stable release (sections 1 to 3 of the macOS runbook, and steps 1 and 2 of
the Windows runbook). Then:

```sh
npm run release:publish:early:mac -- --confirm-public-release="$MARKIE_RELEASE_VERSION"
npm run release:publish:early:win -- --confirm-public-release="$MARKIE_RELEASE_VERSION"
```

These are `release:publish:mac -- --early` and `release:publish:win -- --early`. Use the named
scripts so a forgotten flag cannot publish straight to stable.

The guards are the same as a stable publish: the exact version, clean pushed `main`, credentials,
and exact-commit evidence matching the files on disk. The runner then:

1. checks the version is newer than the stable feed and not older than the early feed;
2. saves the early feed it is about to replace as `.release/<version>/previous-beta-mac.yml` or
   `previous-beta.yml`, once, so a re-run cannot overwrite it;
3. uploads the artifacts and blockmaps, then downloads each and verifies its full SHA-512;
4. uploads the early feed last and waits for it to propagate;
5. writes `.release/<version>/early.json`.

The stable feeds, the website, and `latest.json` are not touched.

`early.json` holds `publishedAt`, `soakUntil`, `soakDays`, `held`, the commit, and for each platform
the feed hash and every artifact's size and SHA-512. `.release/` is gitignored, so this state lives
on the release machine. Promotion has to run on the machine that published early.

### Soak

The soak is `betaChannel.defaultSoakDays` in the manifest, 3 days today. Override it per release
with `--soak-days=<n>` on the early publish. Fractions work: `0.5` is twelve hours.

The clock is per release. Publishing the second platform restarts it from that publish, and both
platforms promote together. A newer early release replaces the older one: the older one is never
promoted, and the newer one starts its own soak.

### Hold

```sh
npm run release:hold -- --version=0.9.0 --reason="crash on launch in 14.2"
npm run release:unhold -- --version=0.9.0
```

A hold stops promotion, including `release:promote --now`. Unholding does not restart the clock: if
the soak already ended, the next scheduler run promotes.

### Stage 3: promote

The scheduler runs this every hour:

```sh
npm run release:promote-due
```

It is idempotent. When nothing is due it reads only `.release/`, touches neither git nor the
network, and prints one line such as `0.9.0 soaking until 2026-10-23T12:00:00.000Z (31h left)`.
Every run appends its line to `.release/promote-due.log`. It exits non-zero only when a due
promotion fails.

By hand, before or after the soak:

```sh
npm run release:promote -- --confirm-promote=0.9.0          # refuses during the soak
npm run release:promote -- --confirm-promote=0.9.0 --now    # skips the soak only
```

Promotion refuses when the release is held, withdrawn, superseded, or a prerelease. It also refuses
when the early feed in the bucket names a different version, and records it as superseded so the
scheduler stops retrying. A missing or unreadable early feed is a plain failure that the next run
retries. Otherwise it:

1. checks `main`, a clean tracked tree, and that the release commit is on `origin/main`;
2. checks the saved early feed against `early.json` and the live early feed against both;
3. downloads every artifact and blockmap again and compares its SHA-512 with the evidence;
4. saves the current stable feed as `previous-latest-mac.yml` or `previous-latest.yml`;
5. uploads the stable feeds last, after every platform has passed;
6. runs the same checks a stable publish runs: feed propagation, `/download`, every download route,
   `/download/latest.json`, and the Windows public feed;
7. writes `public.json` and `public-windows.json`, and marks `early.json` promoted.

A promotion that stopped halfway is finished by running it again. A platform whose stable feed
already holds the identical early feed is skipped.

After promotion, run the user-level checks in section 5 of the macOS runbook and step 5 of the
Windows runbook. They read the saved `previous-latest*.yml`, so they test the update from the
previous stable release.

### Rollback at each stage

| Stage | Command | Effect |
| --- | --- | --- |
| Early, before promotion | `npm run release:rollback:early -- --confirm-rollback=<version>` | Restores the saved previous early feed on each platform, or points the early feed at current stable when there was none. Marks the release withdrawn, so it never promotes. |
| Stable, after promotion, macOS | `npm run release:rollback:mac -- --confirm-rollback=<version>` | Restores `previous-latest-mac.yml`, then verifies the website routes. |
| Stable, after promotion, Windows | `npm run release:rollback:win -- --confirm-rollback=<version>` | Restores `previous-latest.yml`. |

Early users who already installed a withdrawn build keep it until the next release. The channel
deliberately does not downgrade users who are still opted in, because an old early feed could
otherwise pull them back by several versions.

A stable rollback leaves the early feed alone. Withdraw early as well, or ship a fix, so early users
do not stay on the build stable just left.

Versioned artifacts stay in storage at every stage. Removing them is a separate destructive storage
operation and is normally unnecessary.

### Direct stable publish

`release:publish:mac` and `release:publish:win` without `--early` still publish straight to stable.
Use them only when Kirby asks for a release to skip early access. Afterwards the runner brings the
early feed up to the same version when it is missing or older, because early-channel installs read
only the early feed and would otherwise never see a stable hotfix.

### Legacy `X.Y.Z-beta.N` builds

The old prerelease path still works and never promotes:

```sh
npm run release:version -- 0.5.0-beta.1
npm run release:prepare:mac
npm run release:publish:mac -- --confirm-public-release=0.5.0-beta.1
```

`assertVersion` accepts `X.Y.Z-beta.N` and no other prerelease tag. Electron Builder derives the
channel from the tag and writes `beta-mac.yml`, which `macFeedFile()` selects. `0.5.0-beta.1` sorts
below `0.5.0`, so the stable release afterwards is not read as a downgrade. `--early` refuses a
prerelease version.

## Desktop artifact matrix

| Platform | Local targets | Public status | Required native evidence |
| --- | --- | --- | --- |
| macOS Apple Silicon | `dmg`, `zip` | Signed/notarized stable updater | Package smoke and packaged launch on Apple Silicon |
| macOS Intel | `dmg`, `zip` | Included in macOS stable feed | Package smoke and packaged launch through Intel hardware or Rosetta |
| Windows x64 | `nsis`, `zip` | Signed public stable download; auto-update from `windows/latest.yml` as of 0.5.0 | Exact-commit launch smoke on Windows plus Authenticode verification |
| Linux x64 | `AppImage`, `deb` | Private until approved | Exact-commit launch smoke on Linux |

The Per-platform local artifact contract remains available through:

```sh
npm run electron:pack:mac:arm64
npm run electron:pack:mac:x64
npm run electron:pack:win
npm run electron:pack:linux
npm run electron:build:mac
npm run electron:build:win
npm run electron:build:linux
```

Local packaging uses `scripts/local-electron-builder.mjs` with `--publish never`. It strips signing
and notarization credentials and cannot publish. Required local smoke commands include
`npm run electron:smoke:mac:launch` and `npm run electron:smoke:win:launch`; their launch evidence
contains `screenshot.png`.

Expected installer names remain `Markie-<version>-arm64.dmg`, `Markie-<version>-x64.exe`, and
`Markie-<version>-x64.AppImage` for the primary macOS, Windows, and Linux targets.

## One-time credentials

Keep credentials in the gitignored local environment. Never commit or print their values.

```sh
export APPLE_ID="..."
export APPLE_APP_SPECIFIC_PASSWORD="..."
export APPLE_TEAM_ID="..."
export AWS_ACCESS_KEY_ID="..."

```

## Full macOS release

### 1. Re-ground and inspect status

```sh
git switch main
git pull --ff-only
npm ci
npm run release:status
```

Confirm the package version, current commit, public feed version, and website version. A missing or
stale website version means the server route must be deployed before publishing a new app feed.

**Deploy the server before shipping an app build whose sign-in changed.** The desktop Google flow is
split across both: the app mints a `state` nonce and refuses any `markie://auth` deep link that does
not carry it back, and only a deployed server echoes that nonce. Ship the app first and Google
sign-in fails for everyone who updates, with no way to recover from inside the app. `release:status`
does not catch this, so check it by hand whenever `server/src/desktop-auth.ts`,
`src/lib/auth-state.ts`, or the bridge routes in `server/src/index.ts` have changed since the last
deploy.

**Set the assets bucket before the deploy that ships cloud media.** `ASSETS_BUCKET`,
`ASSETS_ENDPOINT`, `ASSETS_KEY_ID`, and `ASSETS_APP_KEY` must already be set on the Railway `api`
service before that deploy goes out; see `deploy/DEPLOY.md`, Assets bucket, for creating the bucket
and the scoped key. Until all four are set the asset routes answer 503 and Markie shows "media pending"
rather than a failure, so this is a one-time setup step, not a per-release check.

The service has no GitHub connection, so nothing deploys on push. Compare the last successful
deployment against the server commits, and deploy if anything is behind:

```sh
railway status                                   # expect project markie / production / api
railway deployment list | head -3                # last SUCCESS date
git log --oneline --since=<that date> -- server/ # anything here is not deployed
railway up server --path-as-root --service api --environment production --ci
```

`--path-as-root` is required: the service builds with `dockerfilePath: /Dockerfile` and no root
directory set, so the archive root must be `server/` or the build cannot find the Dockerfile. The
upload honours `.gitignore`, which is what keeps `server/node_modules` and the local `markie.db` out
of it.

Then confirm the running container, not just the build. `railway logs --deployment` should show
`database already exists, skipping` (the volume survived), `auth schema up to date` (the migration on
boot is idempotent), Litestream replicating, and `markie-api listening`. `curl <api>/health` should
return 200. Schema changes deserve a closer look: the entrypoint migrates on every boot, so a bad
migration takes the service down at start rather than failing loudly beforehand.

### 2. Set the version once

```sh
export MARKIE_RELEASE_VERSION=0.2.10
npm run release:version -- "$MARKIE_RELEASE_VERSION"
```

This updates `package.json`, the root entries in `package-lock.json`, and `mcp/package.json`. Do not
edit those versions separately.

Write release notes from the actual diff since the previous `v<version>` tag. Commit with the Lore
protocol, push `main`, and wait for required CI. The release runner refuses a dirty tree or a commit
that is not exactly `origin/main`.

### 3. Prepare and verify without uploading

```sh
npm run release:prepare:mac
```

This command:

1. runs `npm run release:preflight` for renderer/Electron tests, MCP tests, server tests, lint, and
   the static build;
2. deletes only generated `dist/` output;
3. builds both macOS architectures, signs and notarizes the app bundles, then signs, notarizes, and
   staples the DMG containers, all with `--publish never`;
4. runs package and native launch smoke checks for Apple Silicon and Intel/Rosetta;
5. regenerates DMG blockmaps and updater hashes after stapling, then verifies `codesign`, Gatekeeper
   acceptance, DMG stapling, sizes, updater-feed contents, blockmaps, and SHA-512 hashes;
6. writes ignored evidence to `.release/<version>/local.json` for the exact commit.

The launch smoke fails on a main-process throw even when a window comes up. `main.js` logs
`uncaughtException` and `unhandledRejection` to `markie-crash.log` and keeps running, so every launch
gate reads that log from its throwaway profile and prints the error. The same launch runs on every
PR as the required `mac-launch-smoke` and `launch-smoke` (Windows) checks. A packaging bug therefore
fails the PR that causes it, not the release. 0.9.0 reached this gate with a module missing from the
public asar because nothing had launched the public Mac build before it.

Passing `release:preflight` alone does **not** mean an artifact is signed, notarized, published,
uploaded, deployed, or approved. `release:prepare:mac` is the complete local gate.

The verification-only command is:

```sh
npm run release:verify:mac
```

### 4. Production publish checkpoint

Only after explicit approval. A normal release goes to early access first; see
[Stage 2](#stage-2-publish-to-early-access) and [Stage 3](#stage-3-promote). The direct stable
publish below is for a release Kirby asked to skip early access:

```sh
npm run release:publish:mac -- --confirm-public-release="$MARKIE_RELEASE_VERSION"
```

The runner rechecks clean pushed `main`, credentials, exact-commit evidence, signatures,
notarization, hashes, and the live website contract. It then:

1. saves the previous public updater feed under `.release/<version>/`;
2. uploads versioned DMGs, ZIPs, and blockmaps;
3. downloads every artifact and blockmap and verifies its full SHA-512 against the smoke-tested
   evidence;
4. uploads `latest-mac.yml` last, making the release visible to installed apps;
5. waits for feed propagation;
6. confirms `/download`, `/download/mac`, and `/download/latest.json` resolve the new release;
7. writes `.release/<version>/public.json`;
8. brings the early feed up to the same version if it was missing or older.

The old `npm run electron:release` command is now only an alias to this guarded publisher; it cannot
build and upload in one unverified step. Never use `electron-builder publish` as a dry run: its
standalone publish command uploads the supplied files even when passed `--policy never`.

### 5. Verify the updater notice as a user

Most of this is now automated:

```sh
npm run update:check
```

It downloads the **previous** public release from the same URL a user would, checks it still
passes Gatekeeper, launches it with a throwaway profile against the **live** feed, and waits for
the app to find, download, and offer the update on its own — no prompting, no stubs. It asserts the
notice names the new version and that the install button is offered. The version to update from is
read from `.release/<version>/previous-latest-mac.yml`; override with `--from <version>`.

What it deliberately does not do is click **Restart & Update**: the staged update is discarded with
the temporary profile, so the swap-and-relaunch is still verified by hand. After publication, launch
the previous public Markie version with a clean profile, choose **Markie > Check for Updates**, and
confirm:

1. the new version is found;
2. download completes;
3. the update-ready notice appears;
4. **Restart & Update** installs and relaunches once;
5. **About Markie** reports the new version;
6. file creation, opening, panel navigation, menu dismissal, and window dragging still work.

This is the final user-facing release checkpoint. Keep the screenshot or screen recording with the
release evidence.

### 6. Finalize source control

After public and updater verification:

```sh
npm run release:verify:public -- --version="$MARKIE_RELEASE_VERSION" --deep
git tag -a "v$MARKIE_RELEASE_VERSION" -m "Markie $MARKIE_RELEASE_VERSION"
git push origin "v$MARKIE_RELEASE_VERSION"
```

Create the GitHub release from that tag and attach or link the release notes. Do not attach unsigned
or unverified Windows/Linux artifacts.

## Rollback

If the newly published feed must be withdrawn, explicitly approve rollback and run:

```sh
npm run release:rollback:mac -- --confirm-rollback="$MARKIE_RELEASE_VERSION"
```

This restores the exact previous `latest-mac.yml` saved before publication or promotion and verifies
the previous version through the public feed and website routes. The version comes from the
confirmation flag, so it still works after `main` has moved to the next version. Versioned artifacts
remain in storage; removing them is a separate destructive storage operation and is normally
unnecessary. See [Rollback at each stage](#rollback-at-each-stage) for the early feed.

## Windows release runbook

Windows is a public signed platform: `windows-x64` is `public` in the manifest, the installer is
signed through Azure Trusted Signing, and as of 0.5.0 a packaged Windows install updates itself from
`windows/latest.yml`. Linux update checks stay disabled until it has the same three things Windows
has: a signed artifact, a published feed, and gate evidence.

The list below is the checklist for **every** Windows release, not a one-time switch. All of it has
to hold on the exact release commit:

- a successful native launch smoke on Windows;
- a production Authenticode signature, verified against the signer subject recorded in the manifest;
- installer and update testing from the previous public Windows version;
- public artifact and feed verification equivalent to the macOS runner;
- an explicit production release decision.

The Windows build cannot be produced on the release machine. It is signed by Azure from CI, because
no certificate exists locally and putting one there is not the goal, so the local half of a Windows
release is not "build and upload" but "fetch what CI signed, prove it is what it claims to be, and
publish that".

### 1. Build and sign in CI

Dispatch `.github/workflows/windows-release.yml` on the release commit with `signing: azure` and
`publish_release: true`. It builds the installer, signs it with a short-lived GitHub OIDC credential
(no long-lived secret in the repo), verifies the signature, then installs, launches, and uninstalls
on a Windows runner before publishing the installer to the rolling `windows-signed` prerelease tag.
A run with `signing: none` produces an unsigned installer for testing and must never be published.

### 2. Fetch and verify locally, uploading nothing

```sh
npm run release:prepare:win
```

This downloads only the artifacts named for this exact version from the `windows-signed` tag
(installer, blockmap, feed) into `dist-windows/`, deliberately not `dist/`, which the macOS prepare
deletes wholesale. It then checks the feed version, every SHA-512, and the Authenticode subject
against `codeSigning.subject` in the manifest, and writes `.release/<version>/local-windows.json` for
the exact commit. `npm run release:verify:win` re-runs that verification on its own.

### 3. Production publish checkpoint

Publishing is an external-production action. It needs an explicit release instruction, and the
command needs the exact version. A normal release uses `release:publish:early:win` here and is
promoted later; see [Release stages](#release-stages). The direct stable publish is:

```sh
npm run release:publish:win -- --confirm-public-release="$MARKIE_RELEASE_VERSION"
```

The runner rechecks clean pushed `main`, credentials, and exact-commit evidence. It uploads the
installer and its blockmap, re-downloads each and verifies the full SHA-512 against the local
evidence, and only then uploads `windows/latest.yml`. The feed goes last for the same reason it does
on macOS: it is the pointer, and a pointer published before what it points at is a broken update for
everyone who checks in between. The upload uses a generated `publish-windows.json` config rather
than a command-line override, so a typo cannot write Windows artifacts over the macOS feed.

### 4. Verify in public

```sh
npm run release:verify:public:win -- --version="$MARKIE_RELEASE_VERSION" --deep
```

### 5. Verify the update as a user

Dispatch `.github/workflows/windows-update-check.yml`. It runs the same
`scripts/update-flow-check.mjs` macOS uses, on a Windows runner, which is real Windows: it downloads
the **previous** public installer from the same URL a user would, installs it, launches it against
the **live** feed with a clean profile, waits for the app to find and download the update on its
own, clicks **Restart & update**, and confirms the executable on disk reports the new version and
the app came back.

The assertions are shared with macOS on purpose (`scripts/lib/update-targets.mjs` holds the four
things that genuinely differ: obtaining the previous release, judging its signature, reading the
version off disk, and finding the relaunched process). A claim that holds on one platform and not
the other is then a real difference rather than a difference in what was checked.

Pass the previous public version as the workflow's `from` input:

```sh
gh workflow run windows-update-check.yml --ref main -f from=<previous version>
```

The runner has no `.release/` directory, so without `from` the check stops at "cannot tell which
version to update from" (the 0.5.4 release lost one run to this). Locally the version would be
read from `.release/<version>/previous-latest.yml`, saved by `release:publish:win`. A Windows
release is not complete until this passes.

### Withdrawing a Windows release

```sh
npm run release:rollback:win -- --confirm-rollback="$MARKIE_RELEASE_VERSION"
```

`release:publish:win` and `release:promote` both save the previous `windows/latest.yml` as
`.release/<version>/previous-latest.yml` before replacing it. The rollback republishes that exact
file and verifies the public Windows feed. Versioned artifacts stay in storage either way.

## 0.5.0 server deploy: email verification and the pending-invite backfill

0.5.0 closes a live authorization flaw. Before it, a document shared to an address that had no
Markie account yet became a `pending_shares` row, and whoever registered that address first
inherited the document. Nothing proved they owned the address. From 0.5.0 the server requires proof
of email ownership, and no pending invite is claimed by an account that has not proven it.

This is a production change with a data migration. It is a human checkpoint from start to finish.

### Blocker: the client release ships first, then the server deploy

**Order matters, and getting it wrong breaks signups in the field.** Publish the 0.5.0 desktop
release, and only then deploy the server. There is no version negotiation between the two: the
server changes what it answers, and only a client that knows the new answers can finish a signup.

What the server starts doing:

- a password signup returns no session, because the address is not proven yet;
- a password sign-in on an unproven account is refused with 403 `EMAIL_NOT_VERIFIED`;
- signup mails a one-time code with type `email-verification`.

What the 0.5.0 client does about it: both of those answers route into the existing code view, and it
confirms the address through `POST /api/auth/email-otp/verify-email` rather than the email-OTP
**sign-in** route. That distinction is load bearing. Signing in by code revokes everything an
unproven account accrued, which is how the real owner of an address reclaims an account a squatter
registered, and it is exactly wrong for someone finishing their own signup: it deletes the password
they just chose. Confirming the address proves the same thing and leaves the account alone. Both
behaviors are pinned together in `server/src/claim-verified.test.ts`.

Consequences to expect and to put in the release notes:

- **Users on an older build cannot complete a new signup** once the server is deployed, until they
  update. An older client sends the code to the sign-in route, which is the flow that used to cost
  people their password, and on a shipped build older than 0.5.0 it never routes there at all.
- **Existing accounts are unaffected**, because the backfill below grandfathers every account
  created before the deploy.
- Anyone whose password was already revoked by the old flow sets a new one from **Forgot?** in the
  sign-in dialog. The reset route creates a credential where there is none, so "forgot my password"
  covers "never had one".

### 1. Dry run BEFORE deploying, so review does not become downtime

Between the deploy and step 6, every pre-existing account is unverified and therefore cannot sign
in with its password. That window has to be minutes, not hours, so do the human part first: run
step 4's dry run against a **copy** of the production database, read the report, and resolve
anything flagged (step 5) before the deploy exists. Then the sequence on the live database is
deploy, dry run to confirm, commit, all back to back.

If a flagged row turns up on the live run that the rehearsal did not show, roll the server back
rather than leaving users locked out while it is investigated.

### 2. Deploy the server

Deploy `server/` as normal. Nothing is required in the database for the new code to run: every claim
path simply checks `emailVerified` first. Record the deploy time in UTC ISO form, for example
`2026-09-01T14:32:00.000Z`. That timestamp is the migration cutoff. Everything created before it is
an account that predates verification; everything after it proves its address the normal way.

### 3. Back up, then check the column names

Take a database backup first. Litestream replication is not a substitute for a snapshot taken
immediately before a schema-touching run.

better-auth has changed column casing between versions, so confirm the live schema matches what the
migration reads:

```sql
PRAGMA table_info(user);     -- expect id, name, email, emailVerified, image, createdAt, updatedAt
PRAGMA table_info(account);  -- expect providerId and userId
```

`emailVerified` is an INTEGER 0 or 1, and `createdAt` is an ISO-8601 UTC string, which is why the
cutoff comparison is a plain string comparison. If either has changed shape, stop and fix the
migration before running it.

### 4. Dry run the migration and read the report

```bash
cd server
DB_PATH=/path/to/markie.db node --experimental-strip-types src/migrate-verified.ts \
  2026-09-01T14:32:00.000Z
```

It writes nothing. It prints:

```
migrate-verified audit (cutoff 2026-09-01T14:32:00.000Z)
  accounts to grandfather: 128 (created 2026-02-11T09:03:11.000Z .. 2026-08-30T22:14:02.000Z)
  invites already claimed into shares: 34
  invites still pending (protected from now on): 6
  FLAGGED claimed shares by never-verified accounts: 0
dry run: nothing written. Re-run with --commit to grandfather.
```

Check the account count and date range against expectations. The range should start at the oldest
account and end just before the deploy; an account dated after the cutoff appearing here means the
wrong cutoff was passed.

### 5. If the flagged count is not zero, stop

Zero is the expected result, and it is worth confirming rather than assuming. A flagged row is an
already-claimed share held by an account that never proved the address and has no OAuth account.
That is the signature of the flaw having actually been exercised.

The script exits 2 and **refuses to write in either mode** while any row is flagged, because
grandfathering such an account would turn a stolen claim into a legitimate-looking one. Do not work
around it. Instead:

1. take the flagged list to the owner, with the document, the claiming account, and the address;
2. contact the real owner of each address;
3. revoke the stolen shares (`DELETE FROM shares WHERE doc_id = ? AND user_id = ?`) and consider
   disabling the claiming accounts;
4. re-run the dry run and confirm the count is now zero.

### 6. Commit the backfill

```bash
DB_PATH=/path/to/markie.db node --experimental-strip-types src/migrate-verified.ts \
  2026-09-01T14:32:00.000Z --commit
```

It re-prints the same audit and then reports how many accounts it verified. Exit code 0 means the
write happened; 2 means a flagged row appeared between runs and nothing was written.

### 7. Smoke checks

- An account that existed before the deploy signs in with its password, unchanged.
- A brand new signup receives a code by email, cannot sign in until the code is entered, and can
  sign in immediately afterwards.
- That same brand new account can then sign in **with the password it was created with**. If it
  cannot, the client confirmed the address through the sign-in route instead of the verification
  route and the password was revoked; stop and fix the client before telling anyone to sign up.
- A Google sign-in still works and still picks up documents shared to that address, because the
  provider proved the address.
- The takeover scenario, run by hand against staging if one exists: share a document to an address
  with no account, register that address, list documents, and confirm the document does **not**
  appear. Then verify the address and confirm it does.
- An invite link already sitting in someone's inbox still opens the document for a recipient with
  no account. That path is unchanged on purpose: holding the token is itself evidence of receiving
  mail at the address, and it never converts the invite into an account share.

### 8. Afterwards

The migration is one-time. Once every pre-deploy account is verified, a second run reports zero
accounts to grandfather. Leave the script in the tree: its audit query is the standing way to ask
whether any share was ever claimed without proof.

## API server deploy and rollback

> **2026-10-22: Markie Cloud runs on Fly.io, app `markie-api` (org `zvn-dev`, region `iad`), not Railway.**
> Railway disclosed a credential breach on 2026-10-21; every server secret except Google and email was
> rotated in the move. Deploy from a clean export: `git archive HEAD:server | tar -x -C /tmp/markie-api-fly`,
> then `cd /tmp/markie-api-fly && fly deploy -a markie-api`. Exactly one machine and one volume
> (`markie_data` at `/data`); never scale it while the database is SQLite. `api.markiedocs.com` is a
> CNAME to `5yn0dkw.markie-api.fly.dev`. The Railway sections below are history.


The `api` Railway service is deployed by uploading `server/` from the CLI. Production carries no
commit hash of its own, so every deploy must record one in its message. Released apps going back
to v0.8.0 call this API. The v0.8.0-era server test suite passes against the current server, apart
from a one-time admin script, so treat any change that breaks those tests as a client-breaking
change.

### Deploy

1. Commit everything. Upload only committed code, from a clean export:
   `git archive HEAD:server | tar -x -C /tmp/markie-api` followed by
   `railway up /tmp/markie-api --path-as-root --service api --environment production --ci -m "<what> (<short sha>)"`.
   Never upload the working tree: `server/` holds an untracked local database and env files.
2. Take a snapshot on the volume before any deploy that changes the schema. The 2026-10-20 deploy
   left `/data/pre-deploy-2026-10-20.db`, which holds the full history from before history was
   capped at 20 versions. Keep it.
   The 2026-10-21 deploy, which added the document platform and linked sign-in tables, left
   `/data/pre-deploy-2026-10-21.db` (integrity ok).
3. After the deploy, check that `/health` returns 200, that `/api/docs` returns 401 without a
   token, and that the logs show Litestream writing to `markie-db-age`.

### Backups

Litestream replicates age-encrypted to `markie-db-age/` in the B2 bucket `Markie`. The identity
and the recipient are the `api` variables `LITESTREAM_AGE_IDENTITY` and `LITESTREAM_AGE_RECIPIENT`.
Kirby holds the offline copy of the identity. The key was rotated on 2026-10-21 after the old
identity was exposed in an agent session; generations written before 01:37 UTC that day decrypt
only with the old identity, which Kirby also holds. Always restore with
`litestream restore -config /etc/litestream.yml`, which reads the identity from the config. A bare
replica URL cannot decrypt. A lifecycle rule deletes hidden replica files one day after Litestream
retires them.

### Rollback

- **Code:** redeploy an older commit the same way, from `git archive <sha>:server`. **First copy
  the current `server/litestream.yml` into that export.** Any commit before d659415 replicates in
  plaintext to `markie-db/`, which would put an unencrypted copy of every document back in B2.
- **Data:** the database restores from the encrypted replica, or from a `/data/pre-deploy-*.db`
  snapshot. With the service stopped, copy the snapshot over `/data/markie.db`, remove the `-wal`
  and `-shm` files, `touch /data/.litestream-new-generation`, then start the service.
- **Schema:** the old server ignores the tables newer servers add, so a code rollback needs no
  database change. Document history pruned to 20 versions per document comes back only from a
  snapshot.
- **Volume `api-volume-a5Kl`:** a detached volume created on the service's first day, 2026-06-11.
  Its contents have not been inspected, so it is kept on purpose. Attach it to a temporary service
  and compare it with the live database before anyone deletes it.

## Moving the Cloud hostname

Markie Cloud's API is moving from `https://api-production-602f.up.railway.app` to
`https://api.markiedocs.com`, a name we control, so the backend can change hosts later without an
app release. The code is ready for it:

- The desktop app names `https://api.markiedocs.com` in `electron/cloud-origin.json`, with the Railway
  origin as a legacy alias. Sessions, documents, links and the sign-in `iss` recorded under the alias
  read as Markie Cloud, so nobody is signed out and no document moves.
- The server (`server/src/official.ts`) answers on both names. `/api/*` is served on both. Browser
  pages under `/auth/` and `/account/` that arrive on the name that is not `BETTER_AUTH_URL` get a
  308 to the same path on `BETTER_AUTH_URL`, so Google's state cookie and callback share one host.

Released apps call the Railway hostname for as long as they run. Never remove it from the `api`
service, and never remove the `api` DNS record once a desktop build that uses it has shipped.

Each step below is a human checkpoint. Do them in order and check each one before the next.

1. **Railway custom domain.** On project `markie`, environment `production`, service `api`, add the
   custom domain `api.markiedocs.com`. Railway shows a CNAME target, and possibly a TXT record to
   prove ownership. Note both.
   `railway domain <name> --json` prints only the CNAME. The ownership TXT record
   (`_railway-verify.<label>`) shows up only in the dashboard or the GraphQL `customDomain.status`
   (`verificationDnsHost`, `verificationToken`). Without it the certificate stays at
   `VALIDATING_OWNERSHIP` indefinitely.
2. **Vercel DNS.** markiedocs.com's DNS is on Vercel. Add a `CNAME` record `api` pointing at the
   Railway target from step 1, plus the TXT record if Railway asked for one. Wait until Railway shows
   the domain as active with a certificate, then check
   `curl -sS https://api.markiedocs.com/health` returns 200 and
   `curl -sS https://api.markiedocs.com/api/server-info` names the Railway origin.
3. **Google OAuth.** In the Google Cloud console, open the OAuth client whose ID is the `api`
   service's `GOOGLE_CLIENT_ID`. Under Authorized redirect URIs, add
   `https://api.markiedocs.com/api/auth/callback/google`. Keep the Railway callback URI: a sign-in
   that started before the flip still returns there.
4. **Deploy the server** with this change, following "API server deploy and rollback" above.
   `BETTER_AUTH_URL` still names Railway, so
   `curl -sSI "https://api.markiedocs.com/auth/google-start?state=0123456789abcdef"` answers 308 to the
   Railway origin, while `/api/server-info` answers 200 on both names.
5. **Flip `BETTER_AUTH_URL`** on the `api` service to `https://api.markiedocs.com`. Changing the
   variable redeploys the service. Then check:
   - `/api/server-info` names `https://api.markiedocs.com` on both names.
   - `/auth/google-start` on the Railway name answers 308 to `https://api.markiedocs.com`.
   - Following it lands at Google with `redirect_uri=https://api.markiedocs.com/api/auth/callback/google`.
   - A released app still signs in with email and with Google, and still syncs.

   A Google sign-in that was halfway through during the redeploy fails once. Trying again works.
   To roll back, set `BETTER_AUTH_URL` back to the Railway origin. Both names keep working either way.
6. **Ship the desktop app** that carries this change, through the normal release above. It reaches
   Cloud at `https://api.markiedocs.com` and accepts either name as the issuer, so it works on both
   sides of step 5, but it needs steps 1 and 2 to be live.

Private nightly builds lock to Markie Cloud too. A nightly built from a commit that already checks
`iss` (8ab7abe onward) but predates this change compares it with the Railway origin, so it refuses
Google sign-in after step 5. Ship a nightly with this change before flipping. Released 0.8.x apps do
not check `iss` and are unaffected. Email sign-in is unaffected. The super-nightly gateway's
`PRIVATE_RELEASE_AUTH_ORIGIN` may stay on the Railway origin, since the same API answers there.

markiedocs.com's own Vercel rewrites for `/s/`, `/d/` and `/download` proxy to the Railway hostname.
They keep working and can move to `https://api.markiedocs.com` later, in that repository.
